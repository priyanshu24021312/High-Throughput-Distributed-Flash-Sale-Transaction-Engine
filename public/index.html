Concurrency Engine Architecture

How the Flash Sale System achieves 100% data consistency under high concurrent load.

1

Java Mutex Layer

FlashSale.purchase()

Marked with synchronized. Acts as an application-level mutex gatekeeper so concurrent threads enter the critical section in strict mutual exclusion.

2

Database Row Lock

SELECT ... FOR UPDATE

Pessimistic exclusive row lock on the target product row in MySQL or ReentrantLock in memory, preventing dirty reads or concurrent decrements.

3

Atomic State Transition

UPDATE product SET qty - 1

Decrements quantity conditionally. If quantity hits zero, updates status atomically to 'SOLD OUT'.

4

ACID Two-Phase Commit

con.commit() / rollback()

If quantity is exhausted or user already purchased (UNIQUE(user, item)), transaction automatically rolls back.

❌

Naive Implementation (Lost Update Flaw)

// Thread 1 & Thread 2 arrive at stock = 1
T1: SELECT stock -> reads 1
T2: SELECT stock -> reads 1 (Race window!)
T1: UPDATE stock = 1 - 1 = 0 (Success)
T2: UPDATE stock = 1 - 1 = -1 (OVERSELLING BUG!)

Without mutual exclusion, both threads evaluate available stock as positive simultaneously, causing stock to become negative or overbooked.

✅

Flash Pulse Protected Engine

// Thread 1 enters synchronized section
T1: Acquires Row Lock -> reads 1
T2: Blocked at Lock Queue (Wait state)
T1: UPDATE stock = 0 -> COMMIT -> Releases Lock
T2: Acquires Lock -> reads 0 -> ROLLBACK (Clean 'SOLD OUT')

Serializability ensures every decrement is strictly isolated. Exactly the intended number of tickets are distributed, zero overselling occurs.
